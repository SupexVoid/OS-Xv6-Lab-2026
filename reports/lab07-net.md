# Lab 7：网络驱动

## 实验目的

1. 理解网卡通过 DMA 描述符环与操作系统交换数据的方式；
2. 为 xv6 的 Intel E1000 模拟网卡实现发送与接收路径；
3. 正确处理描述符所有权、环形下标、并发、内存可见性与 mbuf 生命周期；
4. 通过 UDP 回显、并发收发和 DNS 查询验证驱动与协议栈的协作。

## 实验环境

- 代码基线：MIT 6.S081 2021 `net` 分支；
- 主机系统：Windows 11，Linux 环境为 WSL2 + Ubuntu 22.04 LTS；
- 交叉编译器：RISC-V GCC，目标为 64 位 RISC-V；
- 虚拟机：QEMU `virt` 机器、3 个 hart、128 MiB 内存；
- 网卡：QEMU 模拟 Intel E1000，用户态网络后端和 UDP 端口转发；

所有编译、运行和测试命令均在 Ubuntu 终端中执行。QEMU 使用 `user/slirp` 网络后端完成 UDP 端口转发和 DNS 联网测试。

## E1000 与描述符环

驱动和设备共享两个固定长度为 16 的环：

- 发送环 `tx_ring`：操作系统填写待发送帧的物理地址、长度和命令，推进 `TDT`；设备 DMA 读取数据并在完成后设置 `DD`；
- 接收环 `rx_ring`：操作系统预先为每个描述符提供空 mbuf，设备把收到的帧 DMA 到缓冲区并设置 `DD`，驱动处理后推进 `RDT` 归还描述符。

环形下标都使用 `(index + 1) % RING_SIZE` 回绕。`DD` 位不仅表示工作完成，也表示设备已不再访问对应的旧缓冲区，因此它是安全复用描述符和释放 mbuf 的所有权边界。

## 发送路径 `e1000_transmit`

发送流程如下：

1. 获取 `e1000_lock`，读取 `TDT` 所指的下一个描述符；
2. 检查 `DD`。若设备仍占用该槽，释放锁并返回 `-1`，调用方负责释放未发送的 mbuf；
3. 若该槽保存着上一次已完成发送的 mbuf，先释放它；
4. 保存新 mbuf 指针，填写地址、长度以及 `EOP | RS` 命令，并清除 `status`；
5. 执行内存屏障，使描述符内容先对设备可见，再推进 `TDT` 通知网卡；
6. 释放锁并返回 0。

锁覆盖“检查槽位—回收旧缓冲区—发布新描述符—推进尾指针”的完整操作，避免多个 CPU 同时占用同一发送槽。发送成功后不能立刻释放 mbuf，因为设备仍可能通过 DMA 读取它；只有下一次观察到该槽 `DD` 后才能回收。

## 接收路径 `e1000_recv`

中断处理函数循环消费所有已完成的描述符，而不是一次只收一个包：

1. 读取 `(RDT + 1) % RX_RING_SIZE`，若未设置 `DD` 则结束本轮；
2. 保存设备写入的长度、状态和错误位，并取出装有数据的旧 mbuf；
3. 分配一个新 mbuf，把它的地址写回描述符，清空描述符状态；
4. 执行内存屏障后推进 `RDT`，把该槽重新交给设备；
5. 释放网卡锁，再检查 `EOP`、错误位和长度；合法帧设置 `packet->len` 后交给 `net_rx()`，非法帧直接释放。

不能在持有 `e1000_lock` 时调用 `net_rx()`。收到 ARP 请求时，协议栈可能立即生成响应并再次进入 `e1000_transmit()`；若接收路径仍持有同一把锁，就会产生自锁死锁。

若新 mbuf 分配失败，驱动丢弃当前帧、重置旧 mbuf 并把同一缓冲区归还设备，使接收环仍能前进，避免一次内存压力永久耗尽全部接收描述符。

## 实现检查与边界处理

实现过程中重点检查并处理了以下细节：

1. 描述符填写完成后执行内存屏障，再更新 `TDT/RDT`，保证设备不会先看到尾指针而读到半写入描述符；
2. 发送和接收都在共享环状态变化时加锁，同时在调用协议栈前释放锁；
3. 显式清理描述符的校验和、错误和特殊字段，避免复用时继承旧状态；
4. 校验 `EOP`、错误位和包长，对异常帧安全释放；
5. 处理接收缓冲区分配失败，使描述符环不因 OOM 停摆；
6. 中断处理一次消费全部已完成的接收描述符，避免在高负载下积压数据包。

## 遇到的问题与解决方法

### 1. QEMU 缺少用户态网络后端

最初启动时报错：

```text
network backend 'user' is not compiled into this binary
```

使用 `qemu-system-riscv64 -netdev help` 检查网络后端，并在 Ubuntu 中安装带 `libslirp` 支持的 QEMU 组件。确认列表中出现 `user` 后端后，E1000、UDP 端口转发和 DNS 测试均可正常运行。

### 2. 内存屏障的位置

更新尾寄存器等于向设备发布工作。若先更新 `TDT/RDT` 再做屏障，设备可能立即读取尚未完全更新的描述符。正确顺序是先填完描述符，执行 `__sync_synchronize()`，最后写尾寄存器。

### 3. 接收路径潜在的重入死锁

把 `net_rx()` 放在网卡锁内看似可以保护数据，但 ARP 等输入可能同步触发发送。解决方法是先完成描述符替换并归还设备、释放锁，然后再把独立的旧 mbuf 交给协议栈。

### 4. DNS 外部网络抖动

第一次两次评分中，UDP 回显和并发测试都通过，但外部 DNS 响应在 30 秒截止时尚未返回。单独联调已经得到正确 A 记录；保持 MIT 原始 30 秒规则复跑后，完整测试分别在 15.6 秒和 16.1 秒内结束并得到 100/100，确认这是外部 DNS 的瞬时抖动。

## 实验心得

网络驱动的核心不是“复制一个包”，而是协调 CPU、设备和协议栈对描述符及缓冲区的所有权。`TDT/RDT`、`DD` 状态位和内存屏障共同规定了软件与设备交接数据的顺序；接收路径在调用协议栈前释放网卡锁，则避免了 ARP 响应等同步发送造成的重入死锁。
